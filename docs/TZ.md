# Техническое задание (ТЗ) — CV Builder

## 📖 Описание проекта

Необходимо реализовать веб-приложение **CV Builder** (конструктор резюме), требования и дизайн которого представлены в Notion (см. раздел [🔗 Ресурсы](#-ресурсы)).

- **Формат работы:** Парная разработка с другим стажёром (назначается ментором для отработки командного взаимодействия).
  > _Примечание:_ При отсутствии напарника задача выполняется индивидуально в полном объёме до дедлайна.
- **Вводный этап:** После изучения требований обязателен созвон с ментором для согласования стека технологий (UI-библиотека, State Management и сопутствующие инструменты).
- **Дедлайн:** 4 недели с момента старта.

### Data fetching

**Apollo Client не используется.** Проект на Next.js (App Router), поэтому загрузка, кэширование и обновление данных выполняются средствами фреймворка, а не отдельным GraphQL-клиентом с собственным рантаймом:

- **GraphQL-запросы** — тонкая обёртка над `graphql-request` (`server-only`), типы и сами документы генерируются `@graphql-codegen/cli` (`client` preset) из `.graphql`-файлов фич, так что каждый запрос и мутация типобезопасны от схемы до компонента без ручных дженериков.
- **Чтение данных** — запросы к GraphQL-бэкенду выполняются только из **Server Components**, через ту же обёртку над `graphql-request`, без клиентского рантайма и без дублирования кэша.
- **Кэширование и инвалидация** — кэш `fetch` Next.js, на котором построен `graphql-request`: `next: { revalidate, tags }`, `revalidateTag` / `revalidatePath`.
- **Мутации** — **Server Actions**, использующие те же сгенерированные типизированные документы, с последующей инвалидацией затронутых тегов/путей.
- **Клиентское состояние** — только UI-состояние (черновик формы в редакторе, поисковая строка — через `useRouter`/`searchParams`) через согласованный state manager; серверные данные в глобальный клиентский store не дублируются.
- **Авторизация** — access/refresh токены хранятся в `httpOnly`-cookie и читаются на сервере (`server-only` сессионный модуль); токен передаётся в заголовок запроса обёрткой над `graphql-request`, клиентский код токена не видит.

**Почему:** Apollo — тяжёлый клиентский слой с собственным кэшем, который дублирует кэширование Next.js и усложняет SSR. Нативный подход с `graphql-request` + codegen даёт меньше зависимостей, меньше клиентского JS, типобезопасность на уровне схемы и корректную работу SSR/SSG «из коробки».

> ⚠️ Отступление от исходной формулировки требований (там указан Apollo Client) — **согласовать с ментором** до начала активной разработки.

### Архитектура фронтенда: Feature-Sliced Design (FSD)

Код организуется по методологии **Feature-Sliced Design**: слои `app` → `views` → `widgets` → `features` → `entities` → `shared`, слой импортирует только нижележащие.

| Слой     | Расположение   | Назначение                                                               |
| -------- | -------------- | ------------------------------------------------------------------------ |
| App      | `src/app`      | Маршруты и layout'ы Next.js (App Router), тонкие файлы без бизнес-логики |
| Pages    | `src/views`    | Композиция страниц из виджетов и фич                                     |
| Widgets  | `src/widgets`  | Самостоятельные блоки интерфейса (шапка, превью резюме)                  |
| Features | `src/features` | Пользовательские сценарии (редактирование опыта, сохранение резюме)      |
| Entities | `src/entities` | Бизнес-сущности (резюме, пользователь): UI, модель, API                  |
| Shared   | `src/shared`   | Переиспользуемая инфраструктура: UI-kit (shadcn), утилиты, API-клиент    |

Слой `pages` назван `views`, чтобы не конфликтовать с Pages Router Next.js. Работа ведётся **командой из двух человек** (парная разработка, см. раздел «Формат работы»).

  - Корректная настройка маршрутизации (App Router / Pages Router).

  - Кэширование и инвалидация серверных данных средствами Next.js (`fetch` cache, `revalidateTag` / `revalidatePath`).
- [ ] **Функционал:**
  - Полная реализация пользовательских сценариев согласно ТЗ в Notion.
  - Запросы к GraphQL API из Server Components; мутации — через Server Actions.
- [ ] **State Management:**
  - Хранение и обработка глобального и локального состояния приложения.
- [ ] **UI / UX:**

  - Интеграция компонентов из выбранной UI-библиотеки.
- [ ] **Тестирование:**
  - Unit-тесты с покрытием кода более **80%**.
  - _(Extra)_ E2E-тесты на все основные сценарии приложения.
- [ ] **Согласование:**
  - Перед началом активной разработки согласовать с ментором библиотеки (UI, state manager и др.).
